# Harness findings — 29 Jul 2026

First run of the automated extension test harness. 17-route API matrix + a
2-case browser E2E, both against the live tracker.

## Headline: the "No Starlink history on this route" display is misleading on transcons

This is the thing Jeremy saw on SFO→EWR, and the harness reproduced it on four
routes and confirmed it renders in a real browser.

On a route with **no direct** Starlink flight history (the premium transcons —
United flies them on widebodies/757s that are far behind on the Starlink
retrofit), `renderPanel()` in `extension/content.js` prints its empty state:

> No Starlink history on this route yet.

…and then, on the **next line**, appends a connection row whenever
`/api/plan-route` returns a full-coverage itinerary. So the panel literally shows
(verbatim, from the Phase-2 browser run on live data):

```
🛰️ LAX→EWR · Aug 28
No Starlink history on this route yet.
via MCI (connection)
96%
```

A reader is told there is no Starlink on this route, directly above a **96%**
Starlink option via MCI. Same shape on SFO→EWR (55% via GEG+ORD), EWR→SFO (49%
via MCI+LAX) and SFO→BOS (73% via GEG+ORD).

**Why it happens:** `renderPanel()` chooses the empty-state string purely on
`flights.length === 0` (direct history), but the connection row (`itin`) is a
separate block with its own condition (`coverage === "full"`). The two were
written independently and can both be true at once.

**Suggested fix (companion repo, needs your call):** when a connection row will
render and the direct list is empty, the first line should say something like
"No *direct* Starlink flight — best connection below" instead of "No Starlink
history on this route yet." One conditional in `renderPanel()`. This is a copy +
logic change to the extension, so it wants a v2.2.0 (which is already pending for
the `/united/` 301 relink) and your sign-off — I did not ship it.

## What is solid (good news)

- **Endpoint parity is perfect.** Across 26 direct flights, the
  `predict_route_starlink` table % equals `/api/predict-flight` % exactly (Δ=0
  every time). The united.com panel and the Google Flights / Navan chips will
  not disagree for the same flight.
- **The tracker agrees with our roster** on every firm tail sampled:
  UA1's N81107 (tracker "no") is not in our roster; UA1596's N73275 and UA5693's
  N85369 (tracker "yes") are both in it. No `ROSTER-CONTRADICTION`.
- **The normal path displays correctly.** SFO→DEN renders a ranked direct list
  (UA1596 68%, UA1214 41%, …) and the page's "United 1596" text gets a live
  `★ 🛰️ 68%` badge. Positive control passed.
- **The extension loads clean** unpacked in Chrome for Testing — service worker
  registers, zero console errors during the run.

## Lower-confidence / watch items

- **`plan-route` returned 0 itineraries once, mid-matrix, for the transcons,
  then 16/16 full on controlled repeats.** I could not reproduce the empty
  result deliberately, so I am calling it a transient (rate-limit or timeout),
  not a systemic flip. It matters because the extension uses
  `Promise.allSettled` with **no retry** on `plan-route`: when that blip
  happens, an empty-direct route loses even its connection row and shows only
  the bare "No Starlink history" line. A single retry on `fetchPlanRoute` would
  remove the worst case. Recorded as `FETCH-FAILED` by the harness when it
  recurs.
- **Extension `airlines.js` vs site roster drift:** the bundled `airlines.js`
  reports United 481/1808; `wifiodds united/data.json` is at 485 equipped tails
  (updated 2026-07-29). Small and expected (the bundle is a snapshot), but worth
  a periodic re-sync.

## Coverage note

The `check_flight` firm-tail path only exercises within ~48h of departure, so
today's run could only sample near-dated flights. The roster cross-check gets
stronger the more firm tails it sees; re-running closer to real travel dates
widens it.
